**Goal:** Make any answer RCK gives re-executable later with a bit-identical result, so a decision stays defensible years after it was made.

**Architecture:** A `DecisionRecord` pins an answer to the exact substrate state that produced it, via a content hash of that state. Replay loads a **snapshot** by hash, re-runs the query, and compares the answer and derivation exactly. Replay never re-ingests facts.

**Tech Stack:** Python 3.11+ stdlib (`hashlib`, `json`, `dataclasses`) + numpy. No new dependencies.

## Verified state of the codebase

All confirmed by execution this session — do not re-derive:

- **Cross-process determinism holds.** A 201-fact agent saved with `save_session`, loaded in a *fresh Python process*, returned a bit-identical score: `0.11831679195165634` both times. This is the assumption the feature rests on.
- **[R2] Provenance now round-trips.** `save_session`/`load_session` previously persisted the knowledge and belief arrays but **not** provenance, so `explain_why` collapsed to a single `source=unknown (leaf)` node after any reload (measured: 5 records in, 0 out). Fixed in `2b3dfac`; a 3-node derivation is now byte-identical across a `checkpoint()`. Regression tests live in `tests/test_session_provenance.py`. **Without that fix this entire plan was unimplementable** — do not regress it.
- `meta.json` now records the real `rck.__version__` (`15.3.1`); it previously hardcoded `"1.5.0"`.
- **No content hashing of KB state exists.** A grep for `sha256|md5|blake2b.*fact|def .*hash` returns only unrelated symbol-id helpers. Build it.
- `ExplanationNode` (`rck/explain_why.py:25`) is a dataclass — `subject`, `relation`, `obj`, `source`, `confidence`, `children`, `is_leaf`, `note` — and `explain()` iterates a stored **list**, so child order is deterministic (no dict/set iteration).
- `rck/atomic.py` exists. Use `atomic_write_json` for record writes.
- **[R2] These are confirmed NOT to affect `ask_with_idk` and must stay OUT of the hash:** the codebook (atoms are minted deterministically from `blake2b(seed, symbol)`, order-independent), the score calibrator (threaded through chain-walk config, never touched by `ask_with_idk`), synonyms (NL `ask()` layer only), query memory (write-only drift tracking), and the chain cache. Negative facts need no special handling — `deny()` stores through the same `kb.store()` path, so the existing fact-list/`_memory` hash already covers them. An over-broad hash causes false `STATE_MISMATCH`, which is its own failure mode.

## Traps

1. **Do not hash snapshot files.** `meta.json` embeds `saved_at: time.time()` and `np.savez_compressed` output is not guaranteed byte-stable. Hash the **content**: hyper dict (excluding `saved_at`), each shard's `_memory` bytes in shard order, and the canonical fact list in stored order.
2. **Bundling is float addition, which is not associative.** Facts fed in a different order produce a different `_memory`. Replay must load a stored snapshot and must **never** offer replay-by-re-ingest. Any such API silently returns different results.
3. **`_memory` is `float32`.** Assert `dtype == np.float32` and C-contiguity before `tobytes()`, or the hash silently depends on memory layout.
4. **[R2] Do NOT hash `belief_n_shards`.** Verified: 300 `tell_belief` calls grew the belief KB 4→8 shards while `knowledge` stayed at 8 shards / 45 facts, completely untouched. `ask_with_idk` never reads `agent.beliefs` (confirmed — `idk_detection` only calls `kb.query`), so hashing that field invalidates records from provably irrelevant activity. Hash `dim`, `seed`, and `n_shards` only.

### [R2] Design note: resharding and record lifetime

The reviewer flagged that auto-reshard fires during ordinary `store()`, so a growing agent changes its own `state_hash`, and asked whether a long-lived agent therefore invalidates its own historical records.

**It does not, and the design already handles it.** A `DecisionRecord` is only meaningful paired with **the snapshot it was recorded against**. Replay targets a stored snapshot directory, never the live agent (Trap 2). So:

- Record a decision, then checkpoint. Those records replay against **that** checkpoint forever, regardless of how the live agent evolves.
- Replaying an old record against a *newer* snapshot correctly returns `STATE_MISMATCH` — the substrate genuinely moved, and saying so is the honest answer, not a bug.

Make this explicit in `replay.py`'s module docstring and in `DecisionRecord`'s: **a record without its snapshot is not replayable.** Do not add any API that implies otherwise.

### Task 3: Replay and verification

**Files:** `rck/replay.py`; test `tests/test_replay.py`.

```python
def replay(record: DecisionRecord, snapshot_dir) -> ReplayResult
```

Load the session, compute `state_hash`, then:
- Hash mismatch → return **`STATE_MISMATCH`** and **do not run the query**. The substrate is not the one that produced the decision; that is the whole answer.
- Hash match → re-run and compare answer and derivation. `VERIFIED` on exact match, `DIVERGED` (with a diff) otherwise.

`ReplayResult` carries a status enum plus details. **Never raise on mismatch** — a replay tool that throws is unusable for auditing a corpus of records.

**Tests:**
- Record → snapshot → replay → `VERIFIED`.
- Replay against a snapshot with one extra fact → `STATE_MISMATCH`, **and the query was never run**. **[R2]** Spy on **`ShardedKnowledgeBase.query`** specifically. There are three layers between `record_decision` and the KB (`ConsciousAgent.ask_with_idk` → `idk_detection.ask_with_idk` → `ShardedKnowledgeBase.query`); `query` is the only one every possible implementation must hit, so spying anywhere else can pass vacuously.
- Replay in a **fresh subprocess** (see `tests/test_crash_recovery.py` for the pattern) → `VERIFIED`. This is the test that actually proves the product claim.
- An IDK answer replays to `VERIFIED`.

### Task 4: End-to-end audit scenario

**Files:** `tests/test_replay.py`.

One test that reads like the real use case. Build an agent, teach it facts, record a decision that depends on a **multi-hop derivation**, `checkpoint()`, then in a fresh subprocess replay and assert `VERIFIED` **and** an identical derivation tree — same nodes, same sources, same confidences. (This is only possible because of the `2b3dfac` provenance fix; if it fails, that fix regressed — do not weaken the assertion.)

Then mutate the KB (`correct()` a fact), snapshot again, replay the same record against the **new** snapshot, and assert `STATE_MISMATCH`.

That pair is the entire feature: an answer is either reproducible against pinned state, or you are told plainly that the state moved.
