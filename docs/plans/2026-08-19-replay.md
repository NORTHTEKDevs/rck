# Decision Replay Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Make any answer RCK gives re-executable later with a bit-identical result, so a decision stays defensible years after it was made.

**Architecture:** A `DecisionRecord` pins an answer to the exact substrate state that produced it, via a content hash of that state. Replay loads the snapshot **by hash**, re-runs the query, and asserts the answer and derivation tree match bit-for-bit. Replay never re-ingests facts — see the determinism constraint below.

**Tech Stack:** Python 3.11+ stdlib (`hashlib`, `json`, `dataclasses`) + numpy. No new dependencies.

- **No content hashing of KB state exists anywhere.** A grep for `sha256|md5|blake2b.*fact|def .*hash` across all modules returns only unrelated symbol-id helpers. This must be built.
- `ExplanationNode` (`rck/explain_why.py:25`) is a clean dataclass — `subject`, `relation`, `obj`, `source`, `confidence`, `children`, `is_leaf`, `note` — and serializes cleanly to JSON.
- `rck/atomic.py` and `rck/wal.py` now exist (durability, shipped). Use `atomic_write_json` for record writes.

## Traps

1. **Do not hash snapshot files.** `meta.json` embeds `saved_at: time.time()`, and `np.savez_compressed` writes zip entries that are not guaranteed byte-stable across runs. Hashing files would make every snapshot of identical state hash differently. **Hash the content**: the hyper dict (excluding `saved_at`), each shard's `_memory` array bytes in shard order, and the canonical fact list in stored order.
2. **Bundling is float addition, which is not associative.** Facts fed in a different order produce a different `_memory` array. Replay must therefore load a stored snapshot and must **never** offer a "replay by re-feeding the facts" path. Any such API would silently produce different results. This constraint is why the record stores a snapshot hash rather than a fact list.
3. **`_memory` is `float32`.** Hash `arr.tobytes()` only after asserting `dtype == np.float32` and `arr.flags.c_contiguous`, or the hash silently depends on memory layout.
4. **Do not include wall-clock time in the hashed content.** The record itself carries a timestamp for audit, but it must sit outside the hash.

### Task 2: Content hash of substrate state

**Files:** Create `rck/snapshot_hash.py`; test `tests/test_snapshot_hash.py`.

```python
def state_hash(agent) -> str:
    """SHA-256 over everything that can change an answer."""
```

Hash, in a fixed order: the hyper dict (`dim`, `seed`, `n_shards`, `belief_n_shards`) as canonical JSON with `sort_keys=True`; then for each shard in index order, its `_memory.tobytes()`; then the canonical fact list in stored order. Exclude `saved_at` and any wall-clock value.

**Tests — these define the contract:**

- Same agent hashed twice → identical.
- Agent saved, reloaded in the same process, re-hashed → identical (this is what makes replay checkable).
- Adding one fact changes the hash.
- `deny()` changes the hash.
- **Two agents given the same facts in a different order produce DIFFERENT hashes** — assert this explicitly. It is the observable consequence of Trap 2 and documents why replay cannot re-ingest.
- A reshard does **not** change the answer but **does** change shard layout: assert what actually happens and encode it. Determine empirically whether `reshard()` alters `_memory` bytes (it re-bundles, so it almost certainly does). If the hash changes across a reshard, that is correct and must be documented: a snapshot taken before a reshard is not the same substrate state as one taken after.

### Task 4: Replay and verification

**Files:** `rck/replay.py`; test `tests/test_replay.py`.

```python
def replay(record: DecisionRecord, snapshot_dir) -> ReplayResult
```

Load the session from `snapshot_dir`, compute `state_hash`, and:

- If the hash does not match the record's → return a **`STATE_MISMATCH`** result. Do not run the query. This is the honest answer: the substrate is not the one that produced the decision.
- If it matches → re-run the query and compare answer and derivation. Return `VERIFIED` on exact match, `DIVERGED` (with a diff) otherwise.

`ReplayResult` carries a status enum plus details. **Do not raise on mismatch** — a replay tool that throws is unusable for auditing a corpus of records; the caller wants a verdict per record.

**Tests:**
- Record → save snapshot → replay → `VERIFIED`.
- Replay against a snapshot with one extra fact → `STATE_MISMATCH`, and the query is **not** run (assert via a monkeypatched spy that the ask path was never called).
- Replay in a **fresh subprocess** (like `tests/test_crash_recovery.py` does) → `VERIFIED`, proving cross-process bit-identity rather than same-process caching. This is the test that actually proves the product claim.
- An IDK answer replays to `VERIFIED`.

Commit.

### Task 5: End-to-end audit scenario

**Files:** `tests/test_replay.py`.

One test that reads like the real use case: build an agent, teach it facts, record a decision that depends on a multi-hop derivation, checkpoint, then in a fresh subprocess replay the record and assert `VERIFIED` **and** that the derivation tree is identical — same nodes, same sources, same confidences.

Then mutate the KB (`correct()` a fact), replay the same record against the *new* state, and assert `STATE_MISMATCH`. That pair is the whole feature: an answer is either reproducible against pinned state, or you are told plainly that the state moved.
